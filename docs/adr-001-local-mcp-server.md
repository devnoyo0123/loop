# ADR-001 — 앱 내장 로컬 MCP 서버로 같은 Wi-Fi의 AI 에이전트에 기록 컨텍스트 제공

> 날짜: 2026-11-12 · 상태: **채택** (구현 P1~P4 완료 — `docs/mcp-server-plan.md` §3 참조)
> 관련 문서: 상세 설계 `docs/mcp-design.md` · 계획/리스크 `docs/mcp-server-plan.md`

## 배경

Loop의 모든 기록은 폰 로컬에만 존재한다(서버 전송 없음). 사용자는 폰의 기록을
맥의 AI 에이전트(Claude Code, GLM)에 컨텍스트로 넘겨 노트에서 멘탈모델을 구축하는
워크플로우를 원한다. 이때 기록이 폰 밖으로 나가지 않게 하려면 **기기 간 직접 통신**
이 필요하다.

## 결정

Loop Android 앱에 **MCP Streamable HTTP 서버를 내장**한다. 설정에서 토글로 켜면
같은 Wi-Fi의 AI 에이전트가 폰에 직접 붙어 기록을 검색·조회한다.

- 전송: `POST /mcp`, JSON-RPC 2.0, 응답 `application/json` — 최소 구현 직접 작성
  (`initialize`·`tools/list`·`tools/call`·`ping`)
- 도구: **읽기 전용** — `search_records`(FTS5 trigram 재사용), 최근/기간 조회,
  계보(chain) 조회. 좌표 항상 제외, 장소명·날씨 기본 포함(끌 수 있음), 이미지는 개수 메타만
- 보안: Bearer 토큰(영속 + 수동 재발급 + 5회 실패 자동 재발급), `0.0.0.0` 대신
  **Wi-Fi 인터페이스 IPv4에만 bind**, Origin/Host 검사, 기본 30분 자동 종료
- 플랫폼: **Android 전용**(iOS는 백그라운드 소켓 유지 불가 — 메뉴 자체 숨김),
  FGS 타입 `dataSync`
- 클라이언트: `claude mcp add --transport http …`로 최초 1회 등록. 이후에는 폰에서
  토글만 켜면 Claude Code·GLM 등 **여러 에이전트가 동일 엔드포인트를 재사용**한다.
  맥 쪽 워크플로우(연결→기록 수집→노트 정리)는 스킬로 문서화한다.

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| `.looplog` 수동 내보내기 + 파일 동기화(Syncthing 등) | 매번 수동 내보내기, 실시간 검색 불가, 폰↔맥 수동 파이프라인 유지 비용 |
| Termux에서 파일 기반 MCP 서버 | 앱 외부 의존, 공용 저장소로 기록 노출, 사용자 설정 장벽 |
| 클라우드 중계 서버 | 로컬 퍼스트 철학 위반 — 데이터가 서버를 경유함, 운영·보안 비용 |
| `dart_mcp` 등 MCP SDK 사용 | HTTP 서버 지원이 확정되지 않아 착수 시 재검토로 보류. 최소 구현이 의존성도 적고 프로토콜 범위도 작음 |

## 결과

**긍정**
- 기록이 폰 밖 저장소로 나가지 않고 LLM 컨텍스트로 사용 가능 — 유일한 데이터
  출구는 "사용자가 명시적으로 켠 경우, 사용자가 붙인 클라이언트" 하나
- 에이전트 중립(MCP 표준): Claude Code·GLM·향후 다른 클라이언트가 같은 서버 재사용
- 기존 자산 재사용 — 검색·계보 쿼리는 `LoopDb` 메서드 재사용, 스키마 변경 없음

**트레이드오프**
- DHCP로 폰 IP가 바뀌면 클라이언트 등록 URL을 다시 잡아야 함(명령 복사 버튼으로 완화,
  근본 해결은 mDNS 후순위)
- AP isolation 게스트 Wi-Fi에서는 기기 간 통신 자체가 불가(설계 §4.4·§11.3 진단으로 안내)
- 1차는 평문 HTTP + 토큰 — TLS는 후순위
- FGS 상주로 배터리 소모(자동 종료 30분으로 한정)

**후속(후순위)**
mDNS/Bonjour 광고 → TLS(자체 서명+핀) → 이미지 반환 → 쓰기 도구(`add_log`) →
Claude Desktop 공식 연결 가이드. 상세는 `docs/mcp-server-plan.md` §6.
