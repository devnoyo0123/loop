# ADR-003 — PC 연결 중에는 60분(유휴) `dataSync` FGS 세션으로 링크를 붙든다

> 날짜: 2026-11-18 · 상태: **채택 — 구현·단위테스트 완료, 실기기 검증 남음**
> 선행: `docs/adr-002-desktop-mcp-bridge.md`(FGS 제거 결정을 이 문서가 부분 수정) ·
> 상세 설계: `docs/mcp-bridge-design.md` §1.2·§3
> 구현: `android/app/src/main/kotlin/com/loop/loop/PcLinkService.kt`,
> `lib/services/pc_link.dart`(`PcLinkKeeper`, 세션 로직)

## 배경

ADR-002는 폰을 클라이언트로 바꾸면서 ADR-001의 FGS(`dataSync`)를 **유지비·신고 부담을 이유로
제거**했다. 대가는 "앱이 전경일 때만 링크 유지"였고, 설계 문서도 화면 꺼짐·백그라운드 연결을
후순위로 미뤘다.

실사용(2026-11-18, Galaxy Z Fold 6 + 맥 브리지)에서 이 트레이드오프가 **감당할 수 없을 만큼
불편**하다고 확인됐다:

- 화면을 끄거나 다른 앱(대개 Claude 데스크톱·터미널을 보며 폰은 내려놓음)으로 가면
  **20~60초 안에 링크가 끊긴다** — Android가 배경 프로세스를 얼리면서(cached app freezer)
  소켓이 죽고, ping 무응답으로 브리지 쪽도 폰을 잃는다
- `PcLinkController._scheduleRetry`는 배경에서 재시도를 일부러 건너뛴다(얼어 있으면 어차피
  못 붙고 배터리만 쓰므로). 결국 사용자가 폰을 다시 켜고 Loop를 앞으로 가져와야 복구된다
- "Claude에게 기록을 물어보는 동안 폰은 잠들어 있다"가 이 기능의 기본 사용 자세인데,
  그 자세에서 매번 끊기므로 사실상 쓸 수 없다

## 결정

**PC 연결이 붙어 있는 동안에만** Android 포그라운드 서비스(`PcLinkService`, 타입 `dataSync`)를
띄워 프로세스가 얼지 않게 한다. 세션은 유휴 기준 60분으로 묶는다.

- **세션 시작**: 링크가 `connected`가 되는 순간(사용자가 "PC 연결" 화면에서 연결/페어링, 또는
  앱 복귀 시 재연결). **앱이 전경일 때만** 시작한다 — Android 12+ 배경 FGS 시작 제한을 피하고,
  `BOOT_COMPLETED` 등 배경 트리거에서는 절대 시작하지 않는다
- **세션 길이**: 연결 또는 **마지막 도구 질의 후 60분** 조용하면 `disconnect()` + FGS 종료.
  (2026-11-19 30분 → 60분 조정: 회의·점심 같은 공백에 자주 끊겨 재연결 수고가 더 컸다. 앱 PC 연결 화면·알림에 "마지막 사용 후 1시간 유지"를 표시)
  질의를 처리할 때마다 60분 타이머를 새로 건다. 세션 중 자동 재연결(브리지 재시작·Wi-Fi 순단)은
  타이머를 연장하지 않는다 — 링크가 반복 단선돼도 세션이 끝없이 늘어나지 않게
- **세션 중 배경**: 재연결 루프가 배경에서도 계속 돈다(프로세스가 살아 있으므로). 세션이 없으면
  기존 동작 그대로(배경에선 멈추고 복귀 때 즉시 시도)
- **즉시 종료**: 사용자가 끊음(앱 화면 또는 알림의 [연결 끊기]), 재시도 불가 사유
  (`busy`·`too_many`·secret 무효·코드 요구), 재시도 소진, 앱 엔진 종료(최근 앱에서 밀어 닫음)
- **알림**: 저중요도 전용 채널(`loop_pc_link`, 무음) — "PC에 연결됨 / 마지막 사용 후 1시간
  끊겨요" + [연결 끊기] 액션, 탭하면 앱 열기. 8개 언어(ko·en·ja·zh·es·vi·it·hi) 현지화
- **Android 15+ 6시간 한도**: `dataSync`는 24시간 동안 배경 누적 6시간으로 제한된다(사용자가
  앱을 전경으로 가져오면 리셋). 한도에 닿으면 시스템이 `onTimeout(startId, fgsType)`을 부르고
  몇 초 안에 멈추지 않으면 ANR이다 → `onTimeout`에서 Dart에 `timeout`을 알리고 즉시
  `stopForeground` + `stopSelf()`, Dart는 링크를 정상 종료(`bye`)한다. 60분 유휴 세션이라
  하루 6시간을 채우려면 질의가 끊임없이 이어져야 하므로 실사용에서 거의 닿지 않는다
- **실패 폴백**: `startForegroundService`/`startForeground`가 거부되면
  (`ForegroundServiceStartNotAllowedException`, 6시간 한도 소진 상태에서의 시작 등)
  크래시 없이 세션만 포기하고 **기존 동작(전경 전용 유지)으로 계속**한다 — 링크는 끊지 않는다
- **경계**: Dart는 `PcLinkKeeper` 인터페이스로만 서비스를 다룬다(안드로이드 =
  `AndroidPcLinkKeeper`, `app.loop/pclink` MethodChannel / 그 외·테스트 = `NoopPcLinkKeeper`).
  유휴 시간·타이머는 주입 가능 — 세션 로직은 가짜 keeper·가짜 타이머로 단위테스트한다

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 연결 중 화면 켜짐 유지(`FLAG_KEEP_SCREEN_ON`/wakelock) | **Loop가 화면에 떠 있을 때만** 효과 — 다른 앱으로 가면 그대로 얼어 끊긴다. 화면을 계속 켜 두는 배터리 비용도 FGS보다 크다 |
| 맥 쪽 캐시(브리지가 기록 사본을 들고 폰 없이 응답) | "기록은 폰 밖에 저장되지 않는다"는 로컬 퍼스트 약속(개인정보처리방침 §2-2 포함)을 깬다. 동기화·삭제 전파·암호화 문제도 새로 생긴다 |
| FGS 타입 `connectedDevice` | "외부 기기(Bluetooth·USB·NFC 등)와의 연결 유지"용이고, 런타임에 `CHANGE_NETWORK_STATE`/블루투스/USB 등 **선행 조건 권한·상태 중 하나**를 요구한다. LAN 소켓으로 맥에 질의 결과를 주고받는 이 기능은 Play 정책상 "네트워크 데이터 전송" 쪽인 `dataSync`가 맞고, 심사 설명도 일관된다. 대가로 Android 15+ 6시간 한도를 받아들이며 `onTimeout`으로 처리한다 |
| 무기한 세션(사용자가 끌 때까지) | 잊고 둔 연결이 배터리를 쓰고 6시간 한도를 소진한다. 유휴 60분이면 "물어보는 동안"을 충분히 덮는다 |
| ADR-002 그대로(전경 전용) | 실사용 불가 수준 — 배경 참조 |

## 결과

**긍정**
- 화면 꺼짐·다른 앱 사용 중에도 Claude 질의가 폰에 닿는다 — 기능의 기본 사용 자세가 동작
- 세션이 연결 상태·유휴 60분에 묶여 있어 배터리·한도 소모가 질의하는 동안으로 한정된다
- 알림이 "지금 PC가 기록을 볼 수 있다"를 상시 표시 — 프라이버시 측면에서도 투명성이 오른다

**트레이드오프 / 할 일**
- **Play Console FGS 신고 필요**: 정책 > 앱 콘텐츠 > 포그라운드 서비스 권한에서 `dataSync`
  (`FOREGROUND_SERVICE_DATA_SYNC`) 사용 사례 설명 + **데모 영상**(연결 → 화면 끔 → 맥에서 질의 →
  응답 → 알림 [연결 끊기]) 제출. ADR-002가 피하려던 신고 부담을 다시 진다
- 연결 중 상시 알림 1개(저중요도·무음). 알림 권한을 거부한 기기에선 알림이 안 보여도 서비스는 돈다
- 네이티브 코드(서비스·채널) 추가 — 릴리스 전 R8 빌드에서 서비스 시작/종료 확인
  (`proguard-rules.pro`의 `-keepnames class com.loop.loop.**`와 매니페스트 참조로 보존됨)
- 실기기 검증 필요: Android 15 이상에서 화면 끔 60분+ 유지, 유휴 만료, 알림 [연결 끊기],
  `onTimeout`(`adb shell cmd device_config put activity_manager data_sync_fgs_timeout_duration 60000`으로 단축 재현), OEM(One UI) 배터리 최적화 영향
